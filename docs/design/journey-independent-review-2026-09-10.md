# 导航与核心创作页面：独立设计复核

> 历史视觉探索／原型记录（2026-09-10 标注）：本文中的“当前”“下一步”“待评审”指原编写阶段，旧配色、布局、截图和原型路由不再作为现行 UI 规范。当前请看[核心体验 v0.3](scene-walkthrough-review-v0.3.md)、[专项 v0.4](production-detail-design-v0.4.md)及[UI 执行规范](mantine-ui-agent-spec-v0.1.md)；共同语言已确认，无须重新选择 A／B／C。历史测试只证明当时的范围。

日期：2026-09-10。对象：`#/journey/` 当前原型。状态：**评审与修订建议，未改页面，未变更已确认基线。**

## 结论

当前原型做到了部分视觉一致性和制作事实的区分，但不能据此认为已经实现了共同语言，也没有充分证据称其布局最优。助手使用带遮罩、阻断工作区的抽屉，不适合持续创作协作；资产需要按快速引用和持续浏览分别设计。

更有把握的方向是：以内容工作区为中心，当前对象的输入在工作区内；参考浏览与助手按需并排展开；短小的就地操作可以使用浮层；真正需要结束当前操作才能继续的步骤才使用模态交互。面板的显示方式应由任务中的信息依赖决定。

上轮验证主要证明状态隔离、路由和操作路径可以跑通，不能证明屏幕布局支持高效创作。当前助手只有固定建议，也没有覆盖持续对话、跨镜头引用和多结果比较，必须保留这项证据限制。

## 1. 依据与实测

本轮实际打开助手、资产选择，检查画面、控件命中和组件行为。未修改业务输入或页面实现。

在 1366×900 窗口中：

- 当前镜头编辑栏从 x=1010 开始，宽 356px。
- 助手抽屉从 x=946 开始，宽 420px，覆盖全部镜头编辑栏及额外 64px 主工作区。
- 对话层标记 `aria-modal=true`。在画布 SH-04 图片中心进行命中检查，命中的是遮罩，不是图片。
- 助手、资产、场次切换和生成作业共用一个 Drawer 容器，互为单选状态。界面没有同时浏览素材、保留助手和编辑当前镜头的连续路径。
- 资产选择同样覆盖当前已引用的参考与提示词，选择期间无法直接对照这些信息。

证据：[助手打开状态](../../output/playwright/2026-09-10-journey-review/assistant-overlay.png)、[资产打开状态](../../output/playwright/2026-09-10-journey-review/assets-overlay.png)、[当前实现](../../apps/web/src/pages/NavigationJourneyPrototype.tsx)。

当前安装的 Mantine Drawer 默认启用遮罩、焦点约束与滚动锁定；这适合模态任务。组件本身没有问题，任务匹配需要调整。[Mantine Drawer 官方说明](https://mantine.dev/core/drawer/)

## 2. 对共同语言的逐项复核

| 已确认原则 | 本轮判断 | 实際表现 |
|---|---|---|
| 媒体优先、轻包装 | 部分符合 | 完整画幅、轻标题、细选中边界正确；打开助手或资产后工作画面退到灰暗背景，候选主要依靠小缩略图判断 |
| 全局紧凑、局部舒展 | 部分符合 | 项目目录进入场次后收起是有效减负；上下文、工作内容、模式连续占三行，当前输入又被候选、状态、参考和操作压在一个窄栏内 |
| 工具就近展开 | 落实不足 | 工具按需出现，但出现后阻断依赖的工作区；当前编辑始终固定在右侧，画布选中对象与输入的空间联系仍较弱 |
| 形状表达层次 | 基础符合，语义需改善 | 中性表面和不同圆角已有区分；常驻编辑栏内部再包浮动卡片，视觉表达与实际停靠行为并不完全对应 |
| 中性底色、克制用色 | 基本符合 | 明暗共用色阶，状态主要靠文字；没有把媒体加滤镜当作选中态。本轮不是完整对比度或无障碍认证 |

“上下文相关”不要求所有工具都紧贴鼠标；稳定的停靠编辑栏在专业工具中也可以合理。问题在于：该栏已经承载当前任务，却被相关辅助工具覆盖并停用。

## 3. 从任务关系判断交互形式

判断顺序：

1. 操作期间必须同时看见哪些信息？
2. 是否需要继续点击、选择或编辑背景里的对象？
3. 该工具是短暂选择，还是持续参与工作？
4. 面板出现是否会移动用户刚定位的对象、改变当前目标或挤压判断画面的空间？
5. 不同窗口尺寸下，能否维持可读、可操作的工作面积？

例如 SH-04 返工需要：观察手部与钥匙 → 对照参考 → 和助手讨论动作 → 调整提示词 → 检查候选。画面、引用和输入彼此依赖，不能全部按“打开一个抽屉、完成后关闭”的串行方式处理。

模态交互会阻断背景，复杂判断又依赖背景信息时，会增加恢复上下文的成本。非模态也可能遮挡关键内容，因此只去掉灰色遮罩不足以解决问题。[NN/g：Modal & Nonmodal Dialogs](https://www.nngroup.com/articles/modal-nonmodal-dialog/)

## 4. 助手与资产应分别处理

### 助手

持续对话应能与画面并排使用。打开后，用户仍应选择画布节点、查看候选、编辑提示词和加入参考。关闭只收起界面，保留会话和输入草稿。

优先采用可调宽、可收起的右侧停靠区，无背景遮罩。它占用实际布局空间，不叠在镜头编辑栏上。助手收起时主区获得更多空间，不为未来的 Agent 能力默认留一个空白聊天栏。

明确的单次“润色提示词”建议，可以在输入旁轻量展开，无需每次开启完整对话。助手位置与助手能力范围分开决策，不能借调整布局把完整 Agent 执行自动纳入 MVP。

### 资产

| 意图 | 合适形式 | 必要条件 |
|---|---|---|
| 给当前镜头加一个已知参考 | 输入旁的轻量选择器、最近使用、搜索或 @ 引用 | 明确引用目标，选后立即看到参考；不阻断整页 |
| 连续找图、对照多个版本、拖入或替换 | 可收起的素材浏览面板，建议靠左并排 | 保留画面与当前输入，搜索条件和滚动位置可保留 |
| 资产管理、版本整理、分类 | 项目／工作室资产完整页面 | 保持原有管理层级，可返回原场次 |

一次性的完整资源选择可以用模态窗口，条件是决策信息都在窗口内、能直接完成。这个条件不适用于需要同时查看镜头并反复试参考的主要创作路径。

## 5. 推荐工作区与空间预算

建议的职责分布：**左侧按需浏览参考；中央是场次内容和当前对象制作；右侧按需持续对话。**

中央内容区继续支持分镜／画布两种模式：

- 分镜模式：保留有序镜头结构，选中后给当前候选足够的预览与输入空间；六镜头网格适合总览，精修与候选对比需要更聚焦的状态。
- 画布模式：当前节点附近展开短操作；较长提示词用稳定的局部输入区，必要时靠主区底部停靠，避免拖动画布时输入框跟着漂移或遮住目标。
- 两者复用字段、动作、输入草稿、候选与执行状态，不要求控件坐标完全相同。

此方案需要重新分配现有完整右侧编辑栏。保留完整编辑栏后再加助手栏，会形成竞争空间。按当前窗口估算：1366 − 全局栏76 − 素材240 − 编辑356 − 助手360，只剩约334px给内容；这不能满足当前主要创作任务。

将当前输入归入中央制作区后，素材240与助手360同时展开，中央理论上约690px；扣除边距后是否足够判断目标镜头，仍要通过原型检验。宽度是评估参数，不是新定稿尺寸。默认收起辅助面板，窄窗口优先保留当前画面和输入，素材可通过快速选择完成，不强行同时展开所有区域。

### 替代方案的取舍

| 方案 | 收益 | 代价／结论 |
|---|---|---|
| 保持现有遮罩抽屉 | 实现简单，关闭时省空间 | 打断背景操作；持续助手不采用，资源一次选择可保留 |
| 右侧“制作／助手”互切 | 改动小，避免额外一栏 | 无法同时对照建议与完整制作输入，只能作为过渡方案；当前对象预览与轻量输入仍需留在主区 |
| 辅助面板并排＋中央局部制作 | 保留内容、输入和持续协作，可适配两种制作模式 | 需要处理空间收缩和局部输入位置；本轮优先推荐进一步验证 |
| 任意拖动多个浮动窗口 | 个性化自由度高 | 遮挡、窗口找回、键盘顺序和布局保存复杂，当前 MVP 不以此作为默认工作方式 |

## 6. 联动规则比左右位置更重要

- 助手展开后，画布、分镜、播放器和必要输入持续可用；不能把视觉遮罩去掉却留下模态焦点限制。
- 助手收起／展开保留对话、输入、引用及滚动位置。
- 发出的请求记录明确的镜头、候选和参考版本。之后点击另一镜头，不得把已发出的请求或返回结果静默改绑。
- 选中素材库中的资产，属于“浏览素材”；不能因此把当前制作镜头换掉。添加时显示“引用到 SH-04”或“加入本轮助手上下文”。
- 面板出现不自动缩放到全场；优先保持正在查看的对象与用户视野，只在必要时补偿平移。用户主动“适应全场”才改变全局构图。
- 大图预览／候选对比是创作判断入口，不能把它与常驻灰暗遮罩混为一类。
- 选中、采用、剪辑使用、固定稿确认继续分开。状态可简化呈现，但出现不一致时要能清楚解释与明确处理。

TapNow 的官方说明提供了相关任务证据：用户可以在 Agent 输入期间继续从画布选择引用；节点工具用于局部编辑，新结果与原始内容保留以便比较。可借鉴的是对象、引用和结果的联动，不能仅凭面板外观断言某产品最优。[和 Agent 对话](https://docs.tapnow.ai/zh/docs/agent/chat-with-agent)、[生成和编辑图片](https://docs.tapnow.ai/zh/docs/canvas/generate-and-edit-images)

## 7. 对整体方案的再判断

仍建议保留：项目→集→场次的上下文；每场双模式；候选、采用、剪辑与固定稿的区别；独立审阅入口和意见回到制作；项目与工作室资产的管理范围。这些设计与承接团队一场戏的工作目标一致。

需要继续改善：

1. **候选判断面积。** 当前候选按钮约61px宽、媒体72px高，不足以支撑写实人物、动作和道具细节的采用判断；需要放大、播放、并排或来回对比。
2. **局部编辑职责。** 右侧同时堆候选判断、状态、采用操作、参考、输入、计划与连续性；需要按当前动作渐进呈现，保留关键差异而减少常驻噪声。
3. **画布价值尚未充分呈现。** 当前主要是已有镜头和前两项参考的空间摆放。未绑定镜头的探索、独立候选分支与素材复用仍未充分演示，不能凭这个原型证明自由画布设计已成熟。
4. **导航纵向占用。** 场次上下文62px、制作／剪辑45px、模式行约52px，制作前约占159px；评审用的46px顶部栏另计。层级语义合理，物理行数和空白仍可优化。
5. **演示文字影响观感。** 假数据、固定建议和原型说明有必要标明，但正式产品里的创作区应减少解释设计原理的文字。

这些是界面与任务组织的改进，不要求重做领域模型或为本轮引入新的后台系统。

## 8. 下一轮应验证的工作片段

先只验证 SH-04：同时查看候选和钥匙参考，向助手提出修改要求，根据建议调整输入，比较结果，再明确采用。用相同素材、相同窗口，对照现有方案与推荐方案。

检查：

- 打开助手后是否能直接选择节点、加入参考和修改提示词？
- 用户能否说清本次请求的目标，切镜头后有没有误引用／误应用？
- 原本需要反复开关面板的步骤是否减少，是否又引入找窗口或找按钮的成本？
- 1366 宽度下，当前画面、参考与输入是否仍可读；是否有被自动缩放或遮住的关键内容？
- 候选判断是否获得足够画面，是否必须依赖对上一张图的记忆？
- 连续执行两个镜头后，模式、草稿和视野是否保持预期？

当前结论可以明确淘汰持续助手的模态遮罩默认方式。推荐替代布局仍需下一轮可点击原型和目标用户验证，不能提前称为全局最优。
