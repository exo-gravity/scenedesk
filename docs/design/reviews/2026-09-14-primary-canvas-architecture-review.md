# 主创作场景的画布架构审查

日期：2026-09-14。**状态：待用户对齐，仅方案；本审查不启动重构实施。**

审查基线为 `feat/import-task-panel` / `bb618bf9a235b4dbe18710051f9fc42f2dfe0f21`。只读源码与已有验收记录，没有启动测试、浏览器或服务，也没有修改演示数据。当前导入任务面板属于整轮功能，保留并纳入建议。

本文回答 SceneDesk 的结构如何支持以自由画布为中心的体验，不把源码推断当成 LibTV 的真实行为。LibTV 的官方证据与实际界面观察由独立研究记录提供。用户最新允许重新讨论整体场景，但要求先列修改点并对齐，覆盖此前“只按批准布局微调”的限制。

## 结论

当前已经有真实画布、选中与编辑分离、近节点输入、贴右对话助手和持久任务恢复。问题不是缺少这些组件，而是**工作区仍以独立业务页面为组合单位**：镜头生产页、画布输入表单、生成计划/结果页、助手执行/应用页通过容器和模式切换拼在一起。缩小边框和收起字段只能缓解拥挤，不能让它们成为同一张画布上的连续创作过程。

最有价值的方向是：场次进入同一个画布，草稿承担创作输入，连接表达准确引用，结果在起源附近可见，镜头和任务提供导航与核对，助手通过真实对话发起明确的画布动作。底层固定版本、任务身份与恢复协议继续复用。重构的重点应是交互归属和呈现模块，不是重写生成状态机。

## 八个需要对齐的修改点

### 1. 画布成为场次主入口

**当前事实。** `SceneProductionWorkspace.tsx:110` 在没有显式路由及历史偏好时默认 `storyboard`；`239` 起的无画布分支还需明确“创建本场画布”。`645` 起中央区域按提案、画布、候选工作区三者替换。因此画布仍是场次的一种工作模式，而非所有创作的默认承载面。

**建议。** 新进入场次以画布为主，保留原场次身份和已有节点布局；镜头预览、候选、分镜建议改成围绕当前场次的查看与处理入口。空场次首先呈现可行动的创作空间，提供添加文本、媒体、草稿及导入。

**重要区别／待对齐。** “默认进入画布”不等于删除分镜能力，也不意味着打开页面便静默创建镜头或生成任务。是否保留用户上次的分镜模式、无画布场次是否沿现有明确创建动作，需要用户确认。若以后改为自动确保画布存在，须单独覆盖原请求未知时的恢复，不能仅靠页面 mount 发 POST。

**可行性。** 前端入口与空态可以先独立调整；无需迁移现有节点或改变媒体身份。

### 2. 场次全屏布局只保留一层创作导航

**当前事实。** 满高容器与助手贴边已经实现，不能再把它们列为缺失。当前还有应用导航、场次头部、分镜/画布切换、画布工具和不同辅助区；提案可整体替换中央画布。父组件同时管理 dock、编辑对象、选中对象、提案、历史、任务页和助手子页（`SceneProductionWorkspace.tsx:292`、`645`、`751`、`832`）。

**建议。** 场次成为稳定的创作容器：一条轻量场次栏，加左侧工具；画布持续存在。镜头、提案和任务采用明确的检查视图，而不是各自再建立一个“主工作区”。助手继续使用真正的贴右侧栏；节点输入留在画布创作区域。

**重要区别／待对齐。** “全屏”应先明确指占满应用工作区，还是允许用户显式收起应用导航、进入专注场次；不应自动调用浏览器全屏。打开侧栏可以改变画布容器宽度，但不能偷偷改变世界坐标变换、选中对象或自动 fit。窄屏列表与专注编辑是已有退化策略，若改成窄屏完整空间画布，属于额外行为选择。

**可行性。** 可以通过场次容器的统一视图状态先收敛；不必先改 API。

### 3. 节点成为输入单元，而不是表单的定位锚点

**当前事实。** `CanvasBoard.tsx:1363` 将 `CanvasComposer` 与父级传入的 `generation: ReactNode` 直接放入 `CanvasContextualEditor`。前者编辑提示、参考和节点属性，后者来自完整 `MediaGenerationWorkspace`。局部编辑器是独立屏幕坐标 overlay，明确不参与节点测量；节点本身仍主要显示标题、摘要和尝试状态。这是“表单拼接感”最直接的结构来源。

`MediaGenerationWorkspace.tsx:550` 有紧凑呈现，但 `716` 起的固定计划和 `841` 起的任务/结果仍各自渲染纵向 Stack。初始输入变短后，后续阶段仍然进入同一容器中的业务面板。

**建议。** 为文字与三类媒体草稿建立专用节点创作呈现：提示、引用缩略条、模型/必要规格、一个当前阶段主动作组成同一单元；固定计划、任务详情及完整恢复说明由对应检查视图承担。不要继续将两个完整页面缩小后相接。

**重要区别／待对齐。** 真正的“节点内输入”会随画布缩放并影响节点测量，和当前固定屏幕尺寸的近节点 overlay 是两种方案，不能只换名称。推荐讨论：普通缩放下显式编辑节点内的有界输入；提示过长、低缩放或空间不足时，用户明确进入专注编辑。同一编辑会话持续拥有输入与 IME，不随选择、任务返回或展示方式变化重建。

**可行性。** 可复用现有本机交接和生成会话，但必须重新验证节点几何、连线端点、低缩放可读性、长文/IME及多草稿切换。当前 overlay 的几何验收不能直接作为真节点内输入的验收。

### 4. 连接引用以画布直接操作为主

**当前事实。** 当前连线已经有真实引用语义；`CanvasBoard.tsx:1537` 显示引用条，`1660` 起提供逐条用途、启用与移除控件。不是“还没有连接”。但完整语义仍主要依赖参考管理表单，画面中的连线、固定镜头来源、助手附件与镜头绑定分散在不同入口。

**建议。** 连线端点和有效目标反馈承担“连接作为输入”的主要操作；短引用条展示确切来源、用途、启用状态和顺序。点击边或引用打开单项配置，复杂管理另行展开，保留键盘添加与排序入口。

**重要区别／待对齐。** 四类关系不能画成含义模糊的一条线：媒体输入引用、固定镜头来源、助手本轮附件、节点与镜头的生产绑定是不同业务事实。普通选择不自动加入助手；连接不能自动升级资产/镜头版本；不能把未生成草稿当可用媒体。准备计划仍解析并固定当时明确启用的引用。

**可行性。** 首片可以只改变已有引用的交互与投影；若希望任意类型节点间都能传递输出，需先检查实际能力与 resolver 支持，不能仅前端放开连线。

### 5. 结果在起源附近呈现，详情进入任务检查


**当前事实。** 节点显示最近尝试标签，完整结果在 `MediaGenerationWorkspace.tsx:841` 的任务区或 `CanvasMediaGeneration.tsx:114` 的历史区。用户查看结果后，再核对位置并明确放到画布。最近的落点修复已经为整组结果避让既有内容；不要把先前重叠截图当作当前缺陷。

**建议。** 起源草稿附近直接显示对应尝试及其真实结果缩略组，用户能预览、比较、查看固定输入，并明确保留成果。任务面板负责详细状态和恢复，而不是成为唯一能看到成果的地方。新草稿始终与旧尝试区分，成功结果不能把编辑中的提示标成已完成。

**重要区别／待对齐。** “就地呈现”有两种不同承诺：只读投影一个尚未放置的结果组，或任务完成自动写入持久画布节点。建议先采用前者，沿现有明确放置动作保留持久意图；若用户希望自动落节点，应明确接受该行为并另外设计发送前的放置意图。两者都不自动创建 Take、采用候选或替换原媒体。

**可行性。** 可复用现有 Media、原 Job 和 materialize 协议。必须保留原 key/body/revision 的未知恢复及已确认位置，不能因为新视觉布局重算原未知请求。来源删除后，历史结果仍可取回。

### 6. 镜头导航服务于画布，不再形成另一套创作页面

**当前事实。** 底部分镜缩略条属于 `CandidateWorkspace.tsx:160`；同一工作区还常驻接入 `ShotPromptComposer`（`153`）。画布里的“本场镜头”则主要承载连接、固定来源与绑定（`SceneProductionWorkspace.tsx:910`）。候选区和场次区各有 dock 状态并互相关闭（`CandidateWorkspace.tsx:265`），两套页面通过回调维持互斥。

**建议。** 镜头目录以场次内导航、筛选和明确定位为主；选中某镜头可检查其固定版本、候选、参考和采用状态，再显式在画布建立创作草稿。候选大预览与采用对话框可以成为镜头检查模块，避免把整个 CandidateWorkspace 塞入新的小侧栏。

**重要区别／待对齐。** 用户浏览镜头不应默认移动画布或替换当前草稿；“定位该镜头内容”是另一个明确动作。节点关联到镜头不等于生成了候选，候选也不等于采用。旧 Take 的 `shotRevisionId`、原范围与反馈版本必须保持，不能用最新镜头内容替代。

**可行性。** 需要先从既有镜头页提取准确媒体/版本的检查接口，再切换布局；仅隐藏底部表单会丢掉真实创作入口。

### 7. 对话助手用明确的画布动作衔接，而不是另一个表单中心

**当前事实。** 当前助手已是保存真实消息/建议的对话，并有下一条输入、历史建议来源、附件复核和 CAS 写回。`CanvasAssistant.tsx:629` 起是对话日志，`1197` 起是输入区，不能描述成假聊天。父层仍区分“画布对象 / 场次建议”（`SceneProductionWorkspace.tsx:769`）；对话中又嵌入计划执行、任务恢复和目标选择表单，`CanvasAssistant.tsx:949` 的建议应用需要另选目标及方式。

**建议。** 右侧会话以消息、明确附件和精简动作卡为主。需要应用时进入可辨认的“选择画布目标”状态，固定所选目标并显示差异；返回原会话完成确认。计划细节可按需展开，但模型、输入版本、fixture 标识及真正的执行动作必须可核对。场次建议和画布建议是否进入同一会话，可通过有类型的上下文和结果动作讨论。

**重要区别／待对齐。** 当前发送只是准备固定计划，执行和应用分别确认（`CanvasAssistant.tsx:1275`）。视觉上减少表单不能把它悄悄变成自主执行 Agent。任意聊天、自动遍历全画布、自动改节点均不是现有能力承诺；统一聊天外观也不能把分镜 Proposal 与提示 Artifact 混为一类结果。

**可行性。** 先复用当前 CanvasAssistantSession 的真实轮次与应用协议，改动作呈现和目标选择。跨三类有限 AI 的统一对话需要独立接口梳理，不能在布局片中假装已经支持。

### 8. 任务中心成为统一检查入口，操作仍归原任务

**当前事实。** 本轮已有 `SceneTaskPanel.tsx:51` 的“生成记录 / 文件导入”页签；任务按钮展示导入数量与错误，原上传恢复面板已接入。生成历史目前筛选 image/video/audio（`CanvasMediaGeneration.tsx:71`），助手任务在会话中。准确缺口是状态与检查入口仍分散，不是任务中心完全缺失。

**建议。** 任务中心提供只读聚合视图：导入、媒体生成和助手尝试按真实身份列出，失败/未知有可发现的入口，选择条目检查其固定输入和结果。画布只展示与当前对象有关的短状态；任务中心关闭不能让未保存或未知问题完全消失。

**重要区别／待对齐。** 统一视图不建立新的通用 Job，不把上传中、提交未知、供应商运行、归档失败、取消未知合并成一个“处理中”。恢复、取消、取回仍调用原控制器的明确操作。不能给每个节点增加轮询；复用场次列表和按需任务读取即可。

**可行性。** 现有导入/生成页签是可复用基础；助手聚合是新增读模型的范围，应独立验收，保留既有导入任务小修。

## 造成拼接感的模块边界

以下是源码结构判断，不将“文件长”直接判定为坏设计。

| 现有边界 | 调用方需要知道的细节 | 建议收敛方向 |
| --- | --- | --- |
| Scene → CanvasBoard → `generation: ReactNode` | 编辑目标绑定、历史分区、局部保留回调、辅助区安全范围、子树总高度 | 场次只传准确目标与视图状态；草稿创作模块提供统一呈现，避免拼接两个完整表单 |
| CanvasComposer 与 MediaGenerationWorkspace | 提示/模型写画布，固定镜头来源及尝试写独立本机分区；准备前还要等服务端保存 | 将这些顺序封装在创作模块的动作中，保留原存储，不让每种呈现重排流程 |
| CandidateWorkspace 与场次辅助区 | 两个 dock 互关、镜头路由和画布路由切换、独立提示生成页 | 提取镜头检查与固定来源接口，外层只保留一个场次视图状态 |
| 助手对话与画布应用 | 用户通过表单再次选择目标，父层传捕获/定位等回调 | 显式的画布目标选择接口；应用仍由助手固定请求和 CAS 控制 |
| 上传、媒体任务、助手任务 | 各自状态名称、列表和恢复按钮 | 聚合只读展示，动作继续归原任务，避免复制业务状态机 |

## 可交付的重构接口建议

这些是待对齐的接口方向，不是立即新增一批通用框架。

1. **场次视图模块（SceneCreativeSession）。** 只拥有选择、编辑目标、检查对象、辅助视图和专注状态。`select`、`edit`、`inspect`、显式 `locate` 分开；`edit` 负责先等待现有本机保留接口，再切目标。它不拥有供应商状态或媒体写入。这样可以减少父组件对互相关闭 dock 和编辑交接顺序的了解。
2. **草稿创作模块（DraftCreationSession）。** 使用已有的两种真实来源适配器——画布草稿与固定镜头输入——以及现有 GenerationSession。小接口提供可编辑输入、固定尝试摘要、当前可用动作，并封装“保留输入 → 必要的服务端保存 → 准备固定计划”的顺序。节点内与专注模式使用同一会话，不各自创建一份状态。
3. **画布呈现模块。** Board 处理空间、选择、端口与键盘交互；草稿输入、引用配置、结果组是具有明确数据接口的局部呈现。不要把整个业务页作为不透明 ReactNode 交给 Board 后再用 CSS 修高度。节点几何仍由已有画布文档和测量规则负责。
4. **任务读模型与镜头检查模块。** 前者组合现有任务投影，后者读取确切 Take、媒体、范围及固定镜头修订。恢复、采用、反馈与应用等写动作调用原有协议，不迁移进“万能 dispatch”接口。

这里追求的是模块深度与局部性：一个动作背后的保留和确认顺序能在一个位置审查，呈现者不需要知道其内部阶段。不是将现有大组件拆成大量只转发 props 的薄组件，也不新建覆盖所有业务的事件总线。

## 建议实施切片（全部待对齐后再启动）

| 切片 | 可独立交付的体验 | 必须保留的公共行为 |
| --- | --- | --- |
| A：入口与场次容器 | 默认场次画布、一层导航、现有任务面板和贴边助手 | 同一 canvas 身份；侧栏不改 viewport；切对象保留输入；空态可操作 |
| B：节点创作与引用 | 一个完整草稿单元，连接/引用直接操作，明确专注编辑 | image/video/audio 全保留；固定来源；长文/IME；本机失败拒绝切换；未知不重发 |
| C：就地结果与任务检查 | 起源结果组、比较与明确放置，统一状态检查 | 独立 Media；原请求身份和已确认位置；源删除后历史；无自动 Take/采用 |

这是内部渐进交付顺序，不缩减用户要求的整体体验。每片都应完成真实业务链后再替换原呈现；无需为了第一片重写后端，也不能以原型页面替换业务实现。
