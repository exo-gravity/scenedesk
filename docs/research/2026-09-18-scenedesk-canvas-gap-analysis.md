# SceneDesk 画布能力现状与即梦 / LibTV 差异分析

日期：2026-09-18。用途：**说清 SceneDesk 画布现在有什么、和两个参考产品差在哪、哪些该补哪些不该补。**

配套文档：[即梦与 LibTV 画布能力全景清单](2026-09-18-canvas-capability-inventory.md)（两个产品的完整能力表与证据等级）。

| 产品 | 证据强度 | 方法 |
|---|---|---|
| **SceneDesk** | **一手·本机实测** | Playwright 量 DOM 与几何（1600×900）+ 读源码；`output/reviews/2026-09-18-workspace-usability-round-2/canvas-scenedesk-baseline.mjs` |

## 1. SceneDesk 画布现状（本机实测）

### 1.1 入口与页面结构

| 项 | 实测 |
|---|---|
| 入口 | 左侧「画布」→ `/production?scene=<sceneId>&mode=canvas` |
| 组织规则 | **每场一张画布**（已批准：`primary-canvas-approved-2026-09-14.md`） |
| 引擎 | **React Flow**（实测 25 节点 / 5 条边） |

## 3. 差异归类

### 3.1 SceneDesk 独有的（应保留，属领域不变量或业务规则）

1. **短剧领域对象直接建在画布上** —— 镜头节点（SH-01…SH-06）、镜头固定来源、镜头关联。两个参考产品都没有"镜头"这个一等节点类型。
2. **显式采用语义** —— 候选 / 明确采用 / 成片使用的区分。两个参考产品都靠落点或评级隐式表达。
3. **每场一张画布** —— 短剧的组织规则。
4. **画布内上传支持多选 + 队列上限** —— 实测 `multiple` + 上限 20,比两个参考产品的画布内上传更明确。
5. **固定版本引用** —— 资产固定版本与不可变修订是 SceneDesk 的核心不变量。

### 3.2 SceneDesk 缺失但**建议补**（能力缺口，与不变量不冲突）

按实现价值排序（前 3 项投入产出比最高）：

| 优先 | 能力 | 参考 | 为什么值得补 |
|---|---|---|---|
| **P0** | **整组/批量生成** | LibTV `整组执行`/`批量生成` | SceneDesk 现在的「选中并定位整组」只是导航;短剧按场次批量出图是刚需 |
| **P0** | **生成前的模型↔素材校验** | LibTV 6 条文案 | 在参数层就拦住并说明理由,比等生成失败省一次付费尝试 |
| **P1** | **参数分层** | LibTV `data.params.*` vs `data` | 让"改参数形成新尝试"清晰化,也是校验的载体 |
| **P1** | **键盘可达的画布核心动作** | LibTV 快捷键全表 | `Tab` 建节点 / `Enter` 生成 / `L` 连线 / `G` 成组 —— SceneDesk 目前只有 Delete/Escape |
| **P1** | **对齐/分布/自动排列** | 即梦 6+2+1 | 短剧画布节点多,手工摆放成本高 |
| **P2** | **小地图 + 网格吸附 + 连线显隐** | 两家都有 | React Flow 生态标准能力,实现成本低;连线多时显隐开关很有用 |
| **P2** | **复制语义区分**（复制节点 / 复制节点和连线 / 创建副本） | 两家都有 | 「创建副本=复制参数+仅上游连线,不继承任务」直接服务于"换提示词再试" |
| **P2** | **节点重命名** | 即梦 TitleWidget | 画布上直接改名,减少跳转 |
| **P3** | **定价进画布** | 即梦生成面板 | SceneDesk 有估价与执行许可,但画布上看不到 —— 放上去能减少无效尝试 |

### 3.3 SceneDesk 缺失但**建议不补**（与领域模型冲突或超出短剧范围）

| 能力 | 参考 | 为什么不补 |
|---|---|---|
| 星级评级替代采用 | LibTV | 与「明确采用」不变量冲突 |
| 结果自动落画布即隐含采用 | 即梦 | 会让生成结果自动成为成片依据 |
| 无限画布 + 多画布/项目 | 两家 | SceneDesk 是每场一张画布,场次即边界;改成多画布会破坏镜头归属 |
| 时间线节点作为画布节点 | 即梦 | SceneDesk 的排序与选用在镜头列表里(已批准),画布不是剪辑器;**若要做时间线,应是独立工作区而不是画布节点** |
| 导演台 / Director Studio / 720°全景 / 逐帧拉片 | 两家 | 超出短剧 MVP 范围 |
| 会话卡片进画布 + 删会话不删产物 | 即梦 | SceneDesk 助手是侧栏(已批准),把会话变画布节点会污染创作空间 |

## 4. 结论

**SceneDesk 画布的定位是对的,差距集中在"工序效率"而非"模型差异"**:

- 三家**都用节点+连线**,SceneDesk 与 LibTV 甚至**用同一个引擎(React Flow)** —— 差异不在范式。
- SceneDesk **独有的是领域语义**(镜头节点、固定版本、显式采用、每场一张画布),这些是护城河,不能为了对齐竞品而放弃。
- SceneDesk **缺的主要是工序层能力**:批量生成、生成前校验、参数分层、键盘可达、对齐分布、视图辅助(小地图/吸附/连线显隐)。这些**不触碰任何领域不变量**,可以照做。
- 即梦的强项是**把生成参数与价格直接放到画布节点上**(`图片 5.0 Lite · 1:1 · 2K · Current price 3/张`),这是场景化程度最高的做法;SceneDesk 的估价与执行许可目前不在画布可见,值得对齐。
- 两个参考产品在"结果采用"上都比 SceneDesk **弱**(无显式采用),不应反向对齐。
