## 1. 短剧的工序事实（本机核实）

| 事实 | 证据 | 含义 |
|---|---|---|
| **画布只做组织、比较、继续创作;不碰候选与采用** | `CanvasShotConnections.tsx:399`「候选与采用保持分别处理」;`:545`「候选只保存选定区间,不自动采用」 | 这是**既定边界,不是缺口** —— 短剧的采用必须显式 |
| **画布侧没有任何通向候选/采用的路径** | `CanvasBoard.tsx` 搜 `候选/candidate` **零命中** | 用户在画布上做出满意结果后,要**自己切到另一个工作区**再走一遍 |
| **镜头列表按单对象选中** | `ShotListWorkspace.tsx` 的 `selectedId` 传出**单个** `shot.id` | 切换与定位以**单个镜头**为单位 |
| **候选工作区按单对象选中** | `CandidateWorkspace.tsx` 用 `selectedShotId`（单个镜头 id）驱动 | 候选处理以**单个镜头**为单位 |
| **画布生成只有单节点** | 「选中并定位整组」是导航,不是生成 | 一场戏 N 个镜头要点 N 次 |
| **后端没有预算机制,只有配额闸门;两者在画布上都没有呈现** | 见 §1.2 的事实核查 | 花费对用户不可见;真正需要呈现的是配额与阻断原因 |

**结论:整条短剧主链路（生成 → 组织 → 比较 → 选用）都是一次一个镜头、一步一停。** 这不是单点缺失,而是**粒度问题**。

### 1.2 事实核查:预算机制不存在（2026-09-18 第三版勘误）

本节第一版曾写「后端预算机制完整,画布上没有呈现」,依据是 `04-state-execution-and-budget.md:79`。**该说法与仓库现状不符,现予更正。** 逐项核实:

| 原说法 | 实际 | 证据 |
|---|---|---|
| 后端预算机制完整 | 没有 `budgets` 表,没有任何预算持久化 | `packages/database/migrations/` 全目录无 `CREATE TABLE *budget*` |
| 预占与实际消费分离可用 | `reservationStatus: "held"`、`costStatus: "final"` 是合成常量,背后没有预占行 | `apps/api/src/modules/generation/model.ts:66,69-74` |
| 画布未呈现预算 | 预算/预占接口本身未实现:`listBudgets`／`createBudget`／`changeBudget`／`listUsage` 只在契约模块里,`apps/` 内零命中 | `docs/implementation/build_contract.py:575-578`;`grep listBudgets apps/` 无结果 |
| 后端已阻断超预算 | 唯一的闸门是**任务计数**,不是金额 | 下条 |

**真实存在的是配额闸门,按模型能力逐条生效:**

- `generation_submission_allowed(wanted uuid)` —— `0092_async_generation_lifecycle.sql:252`:`daily < max_daily_jobs` 且 `pending < 100`。
- `max_inflight` 在派发时二次校验 —— `0103_canvas_discussion.sql:255-256`。
- 本地夹具种成 `max_inflight=2, max_daily_jobs=100`（`scripts/extend-local-image-fixture.ts:110`）。

**唯一真实的费用字段是硬编码的零:**

```ts
// apps/api/src/modules/generation/model.ts:386-393
const estimate: Schema<"CostEstimate"> = {
  pricingRevision: "explicit-test-fixture/1",
  lines: [], baseCost: zero, holdMargin: zero, totalReservation: zero,
  basisNote: "显式本地测试适配器；没有模型调用与费用，不代表真实模型验收。",
};
```

且该字段**插入后不可变**（`0023_generation_assistance.sql:74,80` 的 `guard_generation_immutable()` 触发器）,所以"刷新估价"必须新建计划。

**对第 1 步的三点影响:**

1. **「合计估价」目前只能是 0 CNY。** 必须沿用该 `basisNote` 的诚实写法,**不得为填满面板而编造价格**。
2. **原「估价是批量前置,否则放大付费风险」的风险判断不成立。** 真实供应商被显式阻断（`model.ts:382-383` 推入 `REAL_PROVIDER_ACCEPTANCE_REQUIRED`,`routes.ts:114-119` 返回 503）。批量放大的是**配额消耗与在飞任务数**,不是花费。
3. **提交前校验该挡的是配额、能力失效、参考素材未验收与画布版本漂移**,不是预算。第 2 步第 7 项与第 4 步第 13／14 项据此重读:呈现的是**配额与阻断原因**,金额部分如实显示为零并注明适配器。

### 1.1 为什么"一次一个镜头"是结构性问题

先排除一个错误理由:**不是速度。** 内部工具、一场戏几十个镜头,点几十次的耗时可以忽略。真正的理由是:

> **场次连续性只在场次内横向成立,不可能在单镜头内验证。**

一场戏里人物服装、场景陈设、光线方向必须一致 —— 而**任何一个镜头单独看都是"对的"**。逐镜头串行必然导致:

1. 在镜头 1 上做**局部最优**判断（这张构图好、这张表情对）,因为看不到镜头 3;
2. 到镜头 3 才发现服装颜色飘了;
3. 回头重做 —— 而前面可能**已按显式采用定稿**。

**这是逻辑上的不可能**:顺序决策 + 逐个定稿,与"保证横向一致性"相矛盾。只要粒度是"一个镜头",连续性就无从判定,因为手上永远只有一张图。而连续性正是短剧工具与"一堆单张图"的区别（产品定位：连续剧的**设定复用、镜头分工、版本决策、变更影响**）。

三个机制层面的后果:

| # | 后果 | 依据 |
|---|---|---|
| 1 | **逐镜头提交会复制"依据"**：每个镜头各提交一次 → 各自固定一份参考版本 → 每次重复都是漂移机会。批量提交则一次传入同一份固定参考版本 | 设计文档「**一次来源可服务多个镜头**,媒体不重复上传」(`scene-canvas-interaction-v0.1.md:27`) |
| 2 | **"哪一个被采用"是场次级问题**：场次尺度上"哪些镜头已有采用、哪些还空着",只有横向看才能回答;逐镜头串行时这个问题在流程里没有位置 | 既有不变量:可用素材／候选选用／**明确采用**／成片使用 |
| 3 | **它决定比较能不能发生**：一组结果同时在场,比较才是决策;一次只看一个,就退化成"接受或重试" | 即梦自报任务规划原文「生成4张……**给用户提供细节质感略有差异的多样选择**」—— 比较被设计进批量里 |

**因此批量的价值不在速度,而在于:它是唯一能让"场次连续性"与"场次级采用状态"成为可判定单位的粒度。**

## 2. 判据

对内部短剧工具,按**这条工序链上单次操作能覆盖多少镜头**排序:

- **粒度粗**（一次管一批镜头）优先于**粒度细**（一次管一个）
- 同粒度下,先补**主链路上**的,再补**画布自身**的
- 花费透明与安全反馈照做,但不因它打断创作动作

## 3. 修正后的顺序

### 第 1 步 —— 把"一次一个镜头"变成"一次一批镜头"（主链路粒度）

| # | 能力 | 现状 | 做什么 |
|---|---|---|---|
| **1** | **按场次/所选镜头的批量生成** | 只有单节点生成 | 选中 N 个镜头节点 → 一次固定 N 份计划,N 次作业;先给出**合计估价**（当前为 0,见 §1.2）与**逐项配额状态**;失败逐项可见、可重试 |
| **2** | **镜头列表与候选的多选与批量动作** | 两者都只有单对象 | 多选镜头 → 批量生成 / 批量查看候选;多选候选 → 批量比较、批量归档;为"整场过一遍"提供路径 |
| **3** | **画布 ↔ 镜头 ↔ 候选 的明确衔接** | 画布侧零路径 | **不自动采用**（守住边界）;但让画布结果能**一键进入候选**、并能**跳回来源节点**;反过来从候选能定位到画布上的生成现场 |

> 这三项是一体的:**没有 #1,批量无从谈起;没有 #2,批量生成出来的东西还得一个个看;没有 #3,画布与选用之间的断点会一直存在。**

### 第 2 步 —— 让批量真正可用（比较与追溯）

| # | 能力 | 做什么 |
|---|---|---|
| **4** | **并列比较多个结果** | 一组结果同屏对比（同一镜头的 N 个尝试 / 同一场景的多镜头）,而不是逐个点开 |
| **5** | **生成溯源可见** | 节点上可查"来自哪个固定版本、哪次作业";候选侧能反查生成依据。短剧要可核查版本 |
| **6** | **参数与节点分层** | 生成器参数（喂模型、过校验）vs 节点属性;让"改参数 = 新尝试"边界清楚 |
| **7** | **生成前可执行性校验** | 素材未验收 / 模型不支持该输入组合 / 参数超限 / 已达任务配额 / 画布版本漂移 —— 提交前说明理由（参考 LibTV 的写法） |

### 第 3 步 —— 画布自身的可用性与效率

| # | 能力 | 说明 |
|---|---|---|
| **8** | **对齐 / 分布 / 自动整理** | 一场戏几十个节点时,手工摆放是纯损耗（即梦 6 对齐 + 2 分布 + 自动排列;LibTV `整理画布 ⌥⇧F`） |
| **9** | **小地图 + 网格吸附 + 连线显隐** | 与 LibTV 同引擎（React Flow）,生态标准能力,成本低 |
| **10** | **键盘可达的核心动作** | 建节点 / 连线 / 成组 / 复制 / 生成 |
| **11** | **复制语义区分** | 复制节点 / 复制节点和连线 / **创建副本（复制参数 + 仅上游连线 + 不继承任务）** —— 直接服务"换提示词再试" |
| **12** | **节点重命名** | 画布上直接改名 |

### 第 4 步 —— 花费可见（信息层，不做闸门）

| # | 能力 | 说明 |
|---|---|---|
| **13** | **节点上显示本次估价 + 项目已消耗/可用额** | 后端已有这些事实。即梦的做法是**把价格印在生成面板上**（`Current price 3 / 张`）而不弹窗 —— 建议取这一档 |
| **14** | **配额已满与阻断原因时的明确反馈** | 后端已阻断;画布上要让用户知道原因,而不是按钮点了没反应 |

## 4. 明确不做

| 不做 | 理由 |
|---|---|
| 星级评级 / 落点即采用 | 与「可用素材／候选选用／明确采用／成片使用」不变量冲突 |
| **把"采用"搬进画布** | `CanvasShotConnections.tsx:399` 已确立**「候选与采用保持分别处理」**;第 1 步 #3 只做**衔接**,不做自动采用 |
| 时间线节点（即梦做法） | 排序与选用在镜头列表（已批准）;若要做时间线,应是独立工作区 |
| 无限画布 + 多画布/项目 | 每场一张画布是短剧组织规则 |
| 导演台 / Director Studio / 720°全景 / 逐帧拉片 | 超出当前范围 |
| 会话卡片进画布 | 助手是侧栏（已批准） |
| 照搬 LibTV 批量触发路径 | 实测 `Ctrl+A` 只选中 1 个、按 `G` 无反应,触发路径未验证 |

## 5. 一条需要单独决策的差异（短剧场景下同样相关）

两个产品都把**创作方法本身做成了可复用对象**（LibTV 的 Skill `/pixar-animated-ad-creator`、工具箱模板 16 项;即梦的技能 `/ 电影级长镜头运镜`、`/ 创作分镜`）。我们的对应物是**创作依据**,是数据而非可执行方法。

短剧是**系列化生产**,同一套打法要在几十场里反复用 —— 所以这件事对短剧同样有价值,但它涉及新增领域对象与契约,**不并入本次画布补完**,作为独立议题排在第 1、2 步之后讨论。

## 6. 第 1 步必须先解的设计冲突（2026-09-18 第三版补记）

第一、二版把批量排进画布时,**漏掉了一条已确认的明文禁止**。落地前必须先解:

| 文档 | 原文 | 性质 |
|---|---|---|
| `docs/implementation/18-canvas-workspace-contract.md:25` | 多选 ── 移动、删除呈现、分组、共同作为参考;**不批量展开输入框、不一键执行多个付费任务** | 纳入实施包 v1.3 的设计基线 |
| `docs/design/core-workspace-recommendation-v0.2.md:119` | 多选只显示移动、收纳、引用等共同操作,不出现多份提示词,**也不引入一键付费批量执行** | 已落实到核心体验 v0.3 并获用户确认 |

同时有三条授权:

| 文档 | 原文 |
|---|---|
| `docs/implementation/01-product-requirements.md:50` | 每个首版执行计划对应一个供应商任务,**批量 UI 可以创建多个独立计划** |
| `docs/design/model-integration-architecture-v0.1-2026-09-15.md:312` | 建议编排成一个 **`GenerationBatch` 下的多个固定计划／作业**,各有输入、费用与恢复身份。**批次只是分组,不是第二套调度**;两项成功、两项失败时保留成功结果,用户只对需要的项发起新计划,**不重跑整个批次** |
| `docs/implementation/09-decisions-and-open-items.md:58` | `PM-02` 第二模型或模式、**批量方法**、自动连续性提醒 —— 当时仍未决 |

**两条禁止约束的是"多选工具条的触发面",不是批量能力本身。** 它们所在的章节就是「多选」,禁的是「框选几下就直接烧掉 N 个付费任务」这个低承诺→高承诺的跳跃。既有单节点流程本来就是两阶段:`MediaGenerationWorkspace.tsx:1236` 的「生成图片」只准备不执行,`:820` 另有「确认执行图片生成」才执行。

**因此第 1 步的批量必须走"N 项明细确认屏",而不是多选工具条:**

| 允许 | 禁止 |
|---|---|
| 多选工具条只提供「查看 N 项的生成计划」导航动作 | 工具条上直接「批量生成」把 N 个任务发出去 |
| 批次确认屏内展示逐项输入、逐项阻断原因、合计、逐项计划身份 | 工具条上批量展开 N 份输入框 |
| 确认屏内显式确认后执行 | 任何自动采用或自动进候选 |

这条约束与 §1.1 的论证一致:批量的价值在**同屏横向依据**,不在省点击。确认屏本身就是那个横向视图。

## 7. 结论

> **短剧的主链路（生成 → 组织 → 比较 → 选用）现在都是一次一个镜头,而连续性无法在单镜头内判定。第 1 步先把粒度改粗:批量生成、镜头与候选的多选批量、画布与候选的明确衔接 —— 这三项合起来才让"场次连续性"与"场次级采用状态"成为可判定单位。批量的触发面是多选之后的 N 项明细确认屏,不是多选工具条上的一键执行（见 §6）。**
>
> **第 2 步让批量可用:并列比较、生成溯源、参数分层、提交前校验。**
>
> **第 3 步补画布自身:对齐分布、小地图吸附连线显隐、键盘、复制语义、重命名。**
>
> **第 4 步花费可见:呈现配额与阻断原因;金额如实显示为零并注明适配器,不做弹窗闸门（见 §1.2）。**
>
> 业务模型的差异（镜头节点、固定版本、明确采用、每场一张画布、画布不做采用）**不需要对齐竞品** —— 那是短剧工具的定位本身。
