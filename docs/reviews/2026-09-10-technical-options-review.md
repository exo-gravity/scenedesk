## 1. 总体判断

**保留架构主干，调整任务执行与媒体编辑策略，补齐画布协作及存储生命周期的定案条件。当前方案足以继续技术设计，尚不足以把所有技术选项一并视为最终确认。**

主干选择与当前产品匹配：React／TypeScript 前端、模块化 Node API、独立执行与媒体 Worker、PostgreSQL、私有对象存储、FFmpeg，以及制作事实独立于画布、采用独立于用片、固定版本审阅。

主要问题在复杂度如何分配：有些底层机制适合复用成熟组件，现稿却展开为自行实现；一些媒体正确性约束应落在固定稿与渲染环节，现稿却让唯一服务端剪辑保存接口强依赖完整归一结果；同场并发编辑的限制也不能只用“CAS 已设计”概括。

本评审按“小型产品研发团队、外部模型 API、短剧优先完整 MVP”提出默认建议。实际研发团队能力、部署地区与商业接入方式尚未确定，这些是可能改变选型的输入。客户团队不设 10 人上限，不据此推导必须微服务或实时共同编辑。

## 3. 系统主干：选择合理，避免不必要的第二套运行体系

### 3.1 TypeScript／Node／Fastify 继续作为默认

本产品大量工作是组织数据、授权、请求外部模型、查询状态、签发媒体访问和协调用户操作。前后端使用 TypeScript 有利于共用契约和时间计算，当前没有必须把整个后端迁到 Python 的依据。CPU 密集的媒体处理交给受限 FFmpeg 进程和独立资源池；有明确 Python 专属算法、模型推理或 SDK 缺口时，再建立对应 Adapter。这个建议来自本项目负载划分；Node 官方也区分 I/O 与计算工作，并要求避免阻塞事件循环。[Node 官方运行模型](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)

Fastify 作为当前默认足够合理。若实际团队已有成熟 Python／Java／NestJS 体系，团队经验可以改变默认；不能仅为统一语言强迫团队重学，也不因产品叫 AI 就默认全部采用 Python。当前不做自托管 GPU 集群、Kubernetes 平台或按每个领域对象拆网络服务。

### 3.2 Module 以业务操作提供能力

一个仓库、一个主业务数据库，API、I/O Worker、媒体 Worker 按运行职责部署。短剧、画布、资产媒体、生成、预算、编辑审阅分别是有明确数据所有权的 Module，而不是必须独立部署的微服务。

外部调用者应使用“准备计划、执行计划、保存画布、采用候选、固定剪辑”这样的操作。跨 Module 事务由少量应用用例组织；路由、UI 和未来 Agent 不需要知道全局锁偏序或直接修改其他 Module 的表。现稿的锁顺序可保留为内部实施协议，不应变成每个调用者都要遵守的一长串步骤。

长期广告复用应优先保持媒体、生成计划、任务、版本和画布能力的可复用性。短剧集场镜及广告营销要求各自拥有语义；当前已经带 Shot 身份的 Take／Selection 等接口不应被宣称可直接完整服务广告，也无须现在构造全业务类型注册中心。

## 4. 数据与协作：关系可靠性和创作体验要分别检查

### 4.1 PostgreSQL 和私有对象存储保留

关系库适合维护成员、权限、镜头、媒体引用、采用、固定版本、费用和事务约束。画布的空间文档及生成输入快照使用带版本的 JSONB；媒体原件、代理和渲染产物进入对象存储，数据库保存受控身份和元数据。不能把带 URL 的任意节点 JSON 当所有业务的唯一事实源。

应用授权与 RLS 两层继续保留，但初版策略应清晰：租户隔离与必要项目范围为基础，复杂共享操作由受控业务操作处理。实际运行连接不可用超级用户／BYPASSRLS／表 owner 冒充隔离成功。PostgreSQL 官方明确这些角色的绕过行为以及 FORCE RLS 的作用。[PostgreSQL 16 RLS](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)

队列通常需要跨租户领取任务：调度身份仅拿最小任务标识，业务执行重新建立可信上下文；不能把跨租户调度权限带进任意媒体或业务查询。数据库访问层和连接池事务封装应通过一次真实跨租户测试后定案，不必先抽象通用 Repository 框架。

### 4.2 整画布 CAS 可以保留，但有明确适用条件

现行 [18 §4](../implementation/18-canvas-workspace-contract.md#4-保存冲突与撤销)选择整文档 If-Match、失败保留本地和手工选择重放。它能发现冲突、防止静默覆盖，和当前“每场主责”的主场景相容；它不能减少不同节点编辑产生的冲突。

具体例子：A 改节点甲的提示词，B 移节点乙。两人都基于 r10；A 保存成 r11 后，B 的保存会失败，尽管两个操作没有业务冲突。恢复界面设计得再清楚，也只是降低冲突处理成本。

**首版默认仍建议整文档 CAS，搭配编辑者提示、明确异步协作定位和可靠草稿恢复；不新增独占锁或 CRDT 作为未经验证的必做项。** 编辑者提示不是互斥锁，不保证没有冲突。若目标团队必须多人持续编辑同一张场次画布，应在实施画布保存前重开选择：按对象／命令控制版本，或针对高频文字协作采用 Yjs 等机制；这将影响现行 API 与验收，不能只在 React Flow 层加一个插件。

Yjs 提供可并发修改与同步的共享数据类型，但业务授权、费用、采用和批准不会由 CRDT 自动变得正确，仍应通过服务器业务操作。[Yjs 官方介绍](https://docs.yjs.dev/)

### 4.3 自动保存历史需要容量与生命周期设计

现稿每次保存递增 revision 并保留整文档，支持最大 4 MiB 文档，持续拖动最多每 5 秒提交；但未给出服务端自动保存历史的完整保留和压缩策略。

假设持续 8 小时、每次均为 4 MiB 全量快照、5 秒一次，未压缩逻辑文档量为 **22.5 GiB／画布日**。这是按配置上限推演，不是日常预测或真实数据库占用；压缩、实际文档体积、停顿和索引都会改变成本。它足以说明“有版本”还需要“版本如何保留”。

建议分别定义：当前文档与最新 revision；近期可恢复的自动保存；周期检查点；被生成计划、审阅、交付实际引用的固定快照。未被引用的自动保存按可配置策略压缩／清理，被业务引用的版本和源媒体保护继续有效。旧基线不再可恢复时必须明确提示，不能偷偷覆盖当前稿。首版不要求引入事件溯源或完整操作日志系统。

## 5. 异步执行：复用调度基础，保留业务恢复协议

**建议优先验证 pg-boss，而不是自行实现通用任务领取、心跳、退避和回收。** 当前骨架尚无成熟自研调度器需要保护，适合在正式实施前做这项裁决。

pg-boss 官方提供在调用者既有事务中执行队列操作的 Adapter。若受限业务角色验证通过，业务 job、预算预占和内部命令可以在同一连接／同一事务提交。这样不需要为同一个内部动作同时建设 outbox 转发、自管 worker_tasks 和第三方队列；项目事件／SSE 的事件 outbox 仍然保留。[pg-boss 事务 Adapter](https://pgboss.io/api/adapters)

必须区分三个完成状态：

1. 队列步骤已完成，例如创建请求获得任务 ID。
2. 供应商视频生成已完成。
3. 平台已经取得、校验并保存媒体，业务生成作业才成功。

提交、延时查询、归档和渲染使用独立短步骤；等待供应商期间归还 Worker 槽位，同时保留正确的供应商在途额度。Worker 并发、请求速率和外部在途任务数是三种限制，不能共用一个 concurrency 参数。pg-boss 也明确其 groupConcurrency 存在竞争下暂时超限的边界，所以不能直接作为严格供应商额度账本。[pg-boss Worker 规则](https://pgboss.io/api/workers)

未知付费提交的现有协议应保留：发送可能成功却未存回执时，重投只推进原任务的查询／核对，不能再次购买。成熟队列也可能重新执行任务；Temporal 的 Activity 也存在重试，任何框架名称都不代替供应商幂等契约。[Temporal Activity Execution](https://docs.temporal.io/activity-execution)

其他候选与真实依赖要求见[独立队列报告](../research/2026-09-10-task-execution-review.md)。其中 pg-boss 12.30.0 的声明要求匹配当前 Node22.23.2／PG16.15；事务、最小权限和故障恢复仍未集成验证。BullMQ 官方已有 PostgreSQL backend，不能再说它一定只能使用 Redis；本轮没有证据证明其入队可进入调用者既有业务事务，因此不自动替换推荐。[BullMQ PostgreSQL backend](https://docs.bullmq.io/guide/postgresql)

Temporal 暂不进入 MVP 默认。只有多阶段持久流程、长期人工等待、复杂补偿或 Agent 恢复成为主要成本，或团队已有运维经验时再评估；不要求提前承诺一个迁移日期。

## 6. 创作前端：组件已选，状态所有权仍需落实

保留 Mantine、React Flow、Media Chrome、dnd-kit 和 TanStack Query 的既有方向。本轮没有重新替换已经讨论过的通用 UI，也不把组件官网示例当生产业务模型。

推荐分开三类状态：

| 状态 | 维护方式 | 禁止的耦合 |
|---|---|---|
| 服务端业务快照 | Query 缓存，服务端授权／版本为准；SSE 提醒重取 | 查询刷新直接覆盖正在编辑的内容 |
| 未提交编辑 | 按场次／对象组织的编辑 store，包含 baseRevision、dirty、pending、撤销与恢复副本 | 用 Query 缓存是否仍存在判断草稿是否应保留 |
| 视图状态 | 当前选择、视口、面板、悬浮和尺寸；按需保存个人偏好 | 平移触发业务采用、缩放使生成计划过期 |

Query 官方默认会在重新挂载、窗口聚焦、网络恢复时重取过期查询，并会清理长期不活跃缓存；因此编辑状态应独立管理。这里讨论的是读取缓存，不把 Query 的读取重试错误描述为默认重试收费写操作。[TanStack Query 默认行为](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)

React Flow 的保存示例能序列化 nodes／edges／viewport，但本项目应有自己的 CanvasDocument 和映射层，仅保存允许的业务草稿及布局字段；已定 18 的设计方向正确。[React Flow 保存示例](https://reactflow.dev/examples/interaction/save-and-restore)

性能要验证媒体负载：画布以缩略图为主，按当前操作挂载播放器；不让几百个视频同时解码。节点更新采用局部订阅和稳定引用，列表虚拟化只解决列表，不替代画布节点和媒体解码管理。React Flow 官方指出频繁节点更新和订阅整个 nodes 数组会带来无关重渲染。[React Flow 性能指南](https://reactflow.dev/learn/advanced-use/performance)

现稿已有 300／2,000 节点的容量测试目标，继续保留“待实测”的标注。当前内存原型用于验证交互，不因没有生产 store 而判为缺陷；应在正式迁移前定好上述状态规则。

## 7. 媒体链路：正确性保留，编辑保存需要分层

### 7.1 最重要的协议调整建议

当前 [06 §5](../implementation/06-api-contract.md)和[11 §6](../implementation/11-transaction-and-implementation-blueprint.md)规定 saveCutDraft 只能接收 ready 的 normalizationId；不完整或待处理影响不能保存到这个可渲染草稿。

这个约束保护了渲染输入，但也意味着**尚未做完的编辑需要另一条可靠恢复路径**。例如用户已重排镜头，字幕暂时超出片尾，随后关闭页面；不能要求先完成所有声音字幕处理，才能保留刚才的工作。

建议明确两层，而不放宽正式渲染规则：

- **工作中的编辑草稿**：允许保存结构及授权合法、但尚不完整或未解决冲突影响的编辑，保留问题清单和原基线；不得发布为可审阅或可渲染版本。
- **经过确认的 CutDraft／固定版本**：继续做范围、权限、时间、音轨和依赖验证；必要归一变化明确确认，审阅绑定渲染后的固定文件。

可以用独立编辑会话草稿表达第一层，也可以重构 CutDraft 状态；不在此次评审中同时实施两套。定案后应同步 API、保存状态和关闭重开验收。单有“浏览器保留 dirty 内容”不能代替明确的恢复范围与服务器保存语义。

常规已准备素材应复用制作副本和纯时间计算；昂贵探测与转码在导入／首次需要时执行并缓存，避免在每次普通保存的关键路径重复等待。现稿已经要求复用，不能误称它每次都会重新转码；需要调整的是唯一保存接口的强前置条件和未完成编辑恢复。

### 7.2 播放组件不能代替剪辑预览引擎

Media Chrome 提供播放器控件，适合单素材和固定成片播放；多片段切换、独立音轨混合、字幕时序和缓冲预载需要本项目另外组织。[Media Chrome 官方能力](https://www.media-chrome.org/)

推荐保留：单素材预览；当前剪辑交互预览；服务端固定稿回放三个明确用途。三者使用同一份经过解释的时间与媒体映射，固定稿为正式审阅依据。不能用多个 video 元素轮换播放的秒数，直接证明帧级准确；浏览器 currentTime 表示的播放位置存在管线更新与定位边界，其小数位数不等于实际呈现精度。[MDN currentTime](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime)

### 7.3 FFmpeg 保留，格式支持按实证扩展

统一输出 profile、整数帧／采样边界、不可变原件、代理和制作副本分离、音轨与字幕显式处理均值得保留。FFmpeg concat 对起始时间戳、对应流参数、音视频长度和不同帧率有明确行为，不能只拼接几条命令就宣布等同当前归一规则。[FFmpeg concat](https://ffmpeg.org/ffmpeg-filters.html#concat)

先验证实际目标服务输出和已承诺导入范围，明确可处理、需显式转换和暂不支持的输入。逐帧源映射与 VFR／非零 PTS 的正确性应单独做媒体验证；不自研编解码，也不宣称锁定一个 FFmpeg 版本自然满足设计。若验证后要缩减已承诺媒体范围，须显式修改产品范围与 AT，不借技术简化悄悄删减。

## 8. AI、接口与部署：补齐几个容易遗漏的接口

### 8.1 模型执行和未来 Agent

Seedance 优先仍成立，但“优先某个品牌”尚未完成具体 API 服务、地区、账号和模式的定案。视频生成、图片编辑、文本结构化辅助的输出与生命周期不同；可共用费用、追踪与持久记录，但不强迫每种文本调用都伪装成长视频任务或都要求 providerJobId。

当前先做范围明确的剧本结构建议、提示准备与返工建议。建议增加可追溯的提示模板版本、实际输入引用、模型与输出 schema 版本、调用记录、人工编辑和最终应用关系；能解释哪次建议进入了哪个生成计划。具体字段是本轮建议，尚未写入现行 OpenAPI。

未来 Skills 和 Agent 通过相同业务操作准备建议与执行受授权命令。权限、固定输入、费用确认与幂等继续由服务器判断；Agent 不直连业务表，也不持有绕过预算的供应商创建通路。首版不要求多 Agent 框架、通用工具市场或任意工作流编排。

### 8.2 契约应该实际接上业务路由

OpenAPI 作为统一公开契约继续保留。当前 Python 生成器是设计工件工具，Node 运行时可直接使用产物；不必为了“全栈 TypeScript”重写已能工作的生成器。但不能再并行手写一套不同的 Zod／TypeBox／DTO 规则。

当前 `packages/contracts/src/validation.ts` 已采用 Ajv2020，而 `apps/api/src/app.ts` 仍只有健康检查和 501 业务占位。这个状态是已知 S0 范围，不是已实现业务的缺陷。首个真实端点应证明请求方言、路径／查询解析、鉴权和输出结构都与契约一致。

Fastify 文档示例使用 JSON Schema Draft 7，Ajv 说明 2020-12 需要对应实例，不能混用前代 Schema；因此不能直接假设把现有 OpenAPI schema 塞入框架默认编译器就完成了接入。请求校验和响应序列化各自检查；数据库授权和业务约束放在结构校验之后。[Fastify 校验与序列化](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)、[Ajv 方言说明](https://ajv.js.org/json-schema.html#draft-2020-12-breaking)

现有 132 个操作是整体设计目录。当前工作包已经按切片安排，应继续坚持；这次主要重审剪辑保存等具体语义，不能因接口多就直接删掉业务，也不需要先实现所有路由再做真实媒体闭环。

### 8.3 部署、身份和费用是实际输入

单地区容器、托管 PG、私有存储及密钥管理适合作为首版默认；具体云、地区、资源规格、恢复承诺和价格需要实际条件。跨境素材访问与模型取件也属于部署适配事实，不能只看服务商品牌。

OIDC 作为身份对接标准合理，但目标用户需要邮箱、手机或微信等什么登录方式尚未定案。先选择支持目标渠道的成熟身份提供方与库，平台维护工作室、项目和角色；不要为一个工作台自行建设完整身份平台。

“工作室提供账号”是试点默认建议，仍是商业接入选择。平台内预算只能约束经平台提交的任务，不能防止用户在供应商控制台继续消费。MVP 保留估计、预占、实际费用来源、未知状态和基本核对，客户钱包、充值、转售与通用财务清算继续分开；实际供应商账单可得性影响自动化程度，未知费用不能填零。

## 9. 定案前最有价值的验证

这些是后续获准进入技术验证后的任务，本轮没有执行。目的在于用一个最小真实切片暴露不可逆的选型成本，不再做仅能点通按钮的演示。

| 验证 | 最小任务 | 必须取得的结果 |
|---|---|---|
| 队列与付费安全 | 同事务入队；创建前后杀 Worker；回调和轮询竞争；用故障模拟供应商 | 无孤立任务、无未经授权重复创建、原任务可恢复；受限角色可运行；在途额度正确 |
| 双模式真实保存 | 两个浏览器编辑同场不同节点／同一节点，切换模式，断网重开 | 修改不丢、不静默覆盖、不触发生成；记录冲突频率和完成任务的障碍，据此确认协作范围 |
| 未完成剪辑恢复 | 重排并产生暂未处理字幕影响，保存工作状态、关闭重开、再修复 | 未完成编辑可恢复，正式 CutDraft／固定稿仍严格；无需先处理完全部问题才能保留工作 |
| 真正的媒体闭环 | 以现有六镜夹具、真实媒体、原音轨＋替代对白＋字幕完成裁切和固定稿 | 实际播放和固定渲染一致；源区间、音画、字幕可核查；VFR／29.97 等既有边界分别出结果 |
| 前端媒体容量 | 固定机器下常用与边界节点量，含真实海报／视频尺寸 | 记录首屏、拖动、内存、播放器实例、文档保存与历史体积；无“节点多＝可同时解码同样多视频”的误判 |
| 契约与隔离切片 | 一个真实授权写接口贯通浏览器、Schema、事务、数据库和任务 | 正反请求与响应一致，跨租户访问被拒绝，框架默认行为不静默改输入 |

## 10. 建议后续如何同步

优先讨论并定案 TR-03 任务执行、TR-05 协作范围、TR-06 保存历史、TR-07 剪辑编辑恢复；再结合团队和部署条件收口其余选型。通过后统一更新 03／04／05／06／08／11／18 和对应 ADR／OpenAPI，保留旧评审原文。

本次新结论保存在本文件与独立队列报告。对产品已确认的每场双模式、轻量剪辑、固定审阅与长期复用没有做范围变更；对现行技术实现策略提出的调整也尚未冒充已确认。最终技术基线应区分“已决定的方向”“待集成验证的组件”“必须取得的外部事实”，三者分别管理。
