# 57 候选意见与固定版本修改建议

2026-09-12。本片补齐 [14 §3](14-scene-mvp-closure.md) 保留的 `prepare_rework`：从真实 Take 意见准备修改建议。基线为 `9ef870c`；后端意见持久化、生成链路和前端由三个 agent 并行实施，主任务完成整合与实际业务验收。以下记录已完成的实现与本机证据；GitHub CI和合入需以对应PR实际记录确认。

## 范围与固定来源

候选意见使用原有 Review／Comment 契约。Review 固定到实际 Take，评论原文及每次修订可以追溯；单条意见可标记已处理。创建意见、标记已处理、AI 建议、候选采用和正式审片决定分别记录。首发不接回剪辑工作稿、固定渲染、成片审批或完整返工交付流程。

用户从具体意见准备修改时，必须固定 `sourceTakeId`、`feedback.reviewId`、`feedback.commentId` 及 `feedback.commentRevision`。Take 的 `shotId/shotRevisionId` 是本次明确镜头来源；镜头后来有新版本，不得替换 Take 原版本。新增的 `ReworkLink.commentRevision` 对其他使用者保持可选，但 `AssistanceRequest.kind=prepare_rework` 必须提供。

固定反馈快照保留原文、版本、Review 的候选身份及可选时间范围，参加实际输入摘要和依赖校验。准备或提交时，意见当前版本必须仍与用户固定版本一致且未处理；变更后明确要求重新核对。旧计划与产物保留原快照、仍可读取，并标示输入已变化；不能用最新评论覆盖历史依据。

`creative-rework/1` 的完整输入摘要由数据库 `rework_input_hash` 统一计算与复核，使用既有 `creative_canonical` 对 JSONB 序列化。这样服务端和数据库约束依据同一表示，旧提示／媒体计划的摘要协议保持原样。意见快照自身的字段与整数时间采用固定结构，正文原样保留。

建议结果沿用 `AssistanceArtifact`，包含提示、参考建议及保留／修改要求。用户可追加人工修订、明确带入下一次媒体生成输入；建议本身不会解决评论、采用候选或替换结果。受控 fixture 只验证业务协议，不能算真实模型效果。

## 创建与页面恢复

每份 Take 同时只允许一个开放意见记录。Review／Comment 创建沿用有限的24小时HTTP回执；评论没有永久创建身份。新页面先保留原正文、请求和首次发送时间，未知时仅允许期限内明确重放原请求；到期后停止创建重放，只读核对列表并保留原文。不能因列表里出现相同文字就认定原创建成功。评论编辑使用原评论版本的 CAS，保存时没有实际改变的请求可返回原版本。

候选修改与普通提示分别保留本机输入，修改建议的媒体生成会话也按候选和评论版本隔离。确认框固定打开的意见版本，执行前重新核对当前来源；来源后来改变时保留旧输入，不能在后台换成新意见继续提交。
