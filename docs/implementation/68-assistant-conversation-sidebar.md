2026-09-15。用户要求优化 AI 对话 UI，并完成实际 UI 验证。本轮延续
[已确认的主创作区](../design/primary-canvas-approved-2026-09-14.md)，调整对话的信息层级和本机状态转换，不新增聊天 API、数据库会话实体或自主执行能力。
用户随后提供 Reelay 截图，明确要求结合 LibTV 对照整合整个侧栏。整体对话结构实现于 `46d89fd`，模型菜单细节收尾于 `15d0950`，下述结构以该轮收尾为准。
本机实现与本轮实际 UI 验证已完成；远端 CI 与合入事实见 [PR #39](https://github.com/exo-gravity/scenedesk/pull/39)。

## 对话与创作入口

- 整体为轻顶部栏、连续消息流和底部统一输入区。顶部集中提供「开启新话题」「查看对话历史」和关闭入口；历史在侧栏内查看，选中固定回复后可聚焦查看、明确引用或返回当前对话。
- 默认自由讨论，未选节点也能发送。输入框内上方放参考、显式引用及可选的短任务标签，中间为正文，模型与必要的目标菜单位于最底行。底行左侧用加号附加参考、用任务图标进入创作任务，右侧为圆形发送按钮。参考可搜索并指定用途；保留未发送文字并沿用当前助手模型，不要求每条消息重选，也不常驻「本条消息设置」大表单。
- 普通第二、第三轮继续使用已核对回复的固定 `replyTo`，但不显示「承接上一轮」附件行。只有用户明确引用或旧草稿中的固定引用显示简短摘要；移除引用只取消下一条消息的承接，不更改已固定输入。
- 「准备画面提示」是明确任务入口，进入后才展示必要的目标能力与参考核对。准备固定计划、执行提示任务、查看建议差异和应用到草稿仍是不同动作；讨论回复不能直接当作可应用的媒体提示。
- 已完成的助手执行默认收起为可展开的「执行记录」，讨论与提示任务采用同一规则，连续消息流优先显示问题和回复。已应用建议收成简短确认，完整差异仍可展开核对；收起记录不删除固定计划、执行事实或应用回执。
- 准备条的「回到自由对话」只改变下一条消息的用途，保留当前消息和历史。它不等同于「开启新话题」。进入提示任务时不携带不兼容的讨论引用；如果没有发送新固定请求，返回讨论会恢复进入前的引用选择。已经提交新提示请求后不会跨用途恢复旧引用。本轮没有自动拼接讨论正文、跨用途继承完整上下文或自动执行媒体生成。
- 场次内「从剧本整理分镜」沿既有入口进入真实任务，返回后仍能继续原对话输入。助手任务与画布、候选采用保持各自的确认边界。

[会话 hook](../../apps/web/src/business/use-canvas-assistant-session.ts) 和

## 图片／视频模型选择的实际范围

自由讨论选择助手模型；进入「创作任务 → 准备画面提示」后，同一底部菜单位选择图片、视频或音频目标模型。组件读取真实能力列表并固定目标 ID／修订，已经接通，不是静态占位。这里为指定目标准备提示，媒体生成仍由画布节点的既有流程发起；不把本次选择描述为聊天中已支持直接生图／生视频。

2026-09-15 用户追加细节检查后，修正了多个演示模型被简化成同名的问题：展开菜单保留完整模型名、演示标识与仅提示目标说明；底部仍用紧凑标签并提供完整名称。图片／视频／音频稳定排序，长列表限高滚动，长名称换行。模型读取中、读取失败及成功空列表分开显示；失败可重新读取且不清掉原选择。历史列表也避免在加载或失败时误报为空。参考横向滚动使用主题细滚条并支持键盘聚焦。固定引用期间不能改目标，取消引用后才允许重新选择。

## 新话题与持久状态

`beginCanvasAssistantTopic` 使用本机 `conversationBoundary` 保存已知计划和回复 ID 的显示分界。
旧计划、作业、固定回复和已经处理的应用记录继续保留，可从历史查看；该分界不是服务端会话，不提供跨设备话题同步或删除历史的语义。
开启新话题保留未发送文字、当前显式参考和模型，清除下一条的 `replyTo`，回到自由讨论。
旧回复晚到时不能重新成为当前回复或自动续接的新来源。刷新后同一本机草稿继续使用该分界，避免旧消息混回新消息区。

三个入口 `beginCanvasAssistantTopic`、`beginCanvasAssistantPrompt`、`beginCanvasAssistantDiscussion`
复用同一可编辑检查和本机保留断言：

- 当前身份访问须为 `ready`；本机写入、发送以及来源预核对进行中不能切换。
- 已发送但尚未核对出计划身份的请求、未结束的作业，以及 `review`／`unknown`／`missing` 的应用意图不能被切换覆盖。
- 已知计划通过原 `revise` 留入历史；仅修改下一条用途时使用 `commitDraft`，不重写已经固定的计划和执行。
- 操作返回成功前，须同时确认当前授权、本机已保存状态，以及完整草稿与预期一致。存储失败会抛出错误；UI 不关闭历史或宣告新话题成功，原意图继续可恢复。
- 新话题还须等待历史列表当前读取完成。读取中或失败时，按钮和实际处理函数都阻止用不完整的历史 ID 集合建立分界。

未发送提示任务的往返使用持久 `discussionReturn`，绑定进入前的计划 ID 与原请求 key，保存自动续聊、明确引用或明确不承接三种选择。
返回仅在身份未变且没有新的引用选择时恢复；刷新不会丢失此判断。开启新话题、实际发送新消息、明确引用其他回复或取消引用都会清除暂存。
本机返回失败保留该暂存，用户可重试；新增计划身份、未知请求和未完成作业仍按原门禁处理。

切换不发送计划、执行、应用或模型请求。讨论的实际发送仍走固定计划与作业；未知结果沿原身份只读核对，不因新话题、刷新或用途切换生成替代请求。
历史回复引用先重新读取确切工件修订、检查当前项目与权限，不以列表缓存授予来源访问。
固定历史链及其上限继续遵守[主画布与自由讨论](65-primary-canvas-and-discussion.md)。

## 本轮复现与修正

行为测试先复现了新话题仍展示原当前工件、准备提示把显式引用误标为自动续聊，以及从准备任务返回讨论仍使用旧目标的边界，随后在公开控制器行为处修正。

后续独立审查发现：完成讨论后进入提示任务但不发送，再返回讨论，画面仍显示原回复，下一次请求却缺少 `assistanceSource`。
控制器「进入提示 → 刷新 → 返回讨论 → 再发送」红测实际失败（36 通过、1 失败），加入上述受原身份约束的持久恢复后通过。
补充验证明确引用／取消、晚到回复、新固定计划、未知新请求、新话题与存储失败；不会根据屏幕上仍有旧回复就自行恢复上下文。

实际浏览器还复现了用途切换的误报：进入准备提示时，唯一目标的默认选择 effect 在
`commitDraft` 完成与精确保留断言之间修改草稿，导致界面已进入提示任务却报告「本机尚未保留本次切换」。
UI 现在将本机切换标为进行中，自动默认选择及输入在此期间等待；切换断言成功后才恢复默认选择。
修正未放宽完整草稿比较，也没有把未保存的新状态算成成功。
