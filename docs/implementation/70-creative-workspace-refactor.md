## 并行实施与合入顺序

用户随后明确要求尽可能并行开发多个 PR。已启动三个独立工作目录／分支：`feat/project-canvas-workspace` 实现 PR-2，`feat/script-docx-import` 实现 PR-3，`feat/creative-workspace-e2e` 建立核心页面自动回归；集成负责人负责 PR-1、设计及端到端验收矩阵、差异审查和合入。E2E 是支持业务切片的额外 PR，不将八个工作包误当作固定八次 GitHub 合入。

- PR-2 与 PR-3 从同一已验证导航基础开发。分别拥有画布作用域与文档导入，不共同修改同一个工作目录。
- PR-2 使用新迁移 0106–0109 范围，PR-3 从 0110 开始；只创建实际需要的迁移。迁移器拒绝晚到的低编号迁移，因此**开发和隔离测试并行，数据库合入与共用环境升级先 PR-2 后 PR-3**。
- 契约先改各自 Python 生成源；集成共享变更后重新生成 OpenAPI／TypeScript，不手工拼接生成产物。关联剧本引用到画布的完整流程在两条线集成后复验。
- 每条分支分别提交、检查、推送和建立 PR。相关 CI、实际页面及恢复用例通过后才合入；不因并行赶进度跳过串行集成。后续 PR-4/5 可分别在剧本表示和画布作用域稳定后继续并行。

用户要求核心设计与页面做端到端测试。具体用例与证据规则见[73 端到端与设计验收](73-creative-workspace-e2e.md)：每个核心页面变更必须验收真实业务操作、持久化与恢复，并查看正式构建是否符合已确认设计；稳定主路径加入自动回归。最终 PR-8 做串联试作，不承担补齐前面所有测试的职责。真实模型测试和受控 fixture 测试分别记录。

## 首阶段明确的工程选择

1. 新导航仅在项目浏览页替换原双侧栏；原制作页在 PR-2 接入同一壳层前保留原退出屏障。PR-1 的画布入口读取已有项目/集场数据，显式进入既有场次画布，不静默创建空场次或业务对象，也不声称无场次创作完成。
2. 项目卡片先打开剧本；「画布」与「项目资产」始终可达。场次管理与项目设置保留次级入口，旧 `/content`、`/production`、`/media` 和带固定修订的链接继续解析。
3. 画布本体、生成、助手和镜头领域的变化分别随所属 PR 落实，不借导航替换降低原恢复能力。正式画布侧栏的新跳转须调用现有保留屏障，不能只写 `location.hash`。
4. `.docx` 是首个本地格式；剧本默认阅读、明确重新导入。正文编辑和其他格式仍按实际需要裁决，现有历史编辑代码保留。飞书凭据在配置渠道提供，不写入项目或聊天日志。
5. 首批模型优先按用户已有使用场景评估 Seedream 图片、Seedance 视频；Kling 及其他图片模型保持后续 Adapter 接入范围。具体版本、模式、官方/聚合渠道与消费额度必须核实后记录，未在本 PR 中替用户购买或启用供应商。

## 必须同步的契约

PR-2 更新画布工程契约、领域关系、API 生成源、数据库约束和受限角色授权。PR-3/4 更新 ScriptRevision 来源、原件/显示表示/规范引用文本的对应关系，不将上传文档直接塞进既有媒体允许列表而绕过文件安全与授权。PR-5 更新生成意图、固定输入及结果展示/放置协议，查询、归档重试与新生成语义独立。PR-6 保留 Selection、Take 与 Media 之分。适用修订写在原契约对应章节及实现说明中，避免本计划成为第二套技术真相。

## 需要提前准备的真实验收材料

- 团队实际 `.docx` 样本和版式要求；至少涵盖对白、标题、表格或图片中的实际用法。
- 实际飞书文档类型、租户和应用可读取授权；验证不可读与撤权情形。链接本身不构成读取许可。
- 首批模型服务、地区/账号条件、能力版本及授权消费上限。未具备时继续实现受控契约与恢复测试，真实调用保持未验收。

这些条件不阻塞导航、画布关系与文件导入的独立工作，不通过假内容掩盖缺口。
