# 84 画布第 1 步剩余部分：镜头候选的挑选与画布—候选衔接

日期：2026-09-20 立项，2026-09-21 收口。来源计划：[画布后续能力 review](../research/2026-09-18-canvas-next-capabilities-review.md)（定稿）第 1 步。

状态：**已实施，范围在实施中收窄**。§1–§7 保留立项时的范围与约束作为历史；实际交付以 §8 为准，中途建成又移除的部分记在 §9，延后事项记在 §10。

**本工作项立项时覆盖第 1 步的 #2 与 #3。** #1（批量生成）已由 PR #63 合入 `main`。

## 1. 为什么这三项是一体的

定稿计划的判据是**粒度**：短剧主链路（生成 → 组织 → 比较 → 选用）原本一次只处理一个镜头，而**场次连续性不可能在单镜头内判定**——任何一个镜头单独看都是"对的"。所以第 1 步要把粒度改粗。

三项的分工：

| # | 能力 | 立项时现状 | 缺了会怎样 |
|---|---|---|---|
| 1 | 按场次／所选镜头的批量生成 | ✅ 已合入（PR #63） | 批量无从谈起 |
| **2** | **镜头列表与候选的多选与批量动作** | ❌ 未做 | **批量生成出来的东西还得一个个看** |
| **3** | **画布 ↔ 镜头 ↔ 候选 的明确衔接** | ❌ 未做 | 画布与选用之间的断点一直存在 |

## 2. 范围（立项时）

### #2 多选与批量动作

- 镜头列表：多选镜头 → 批量生成（进入既有的 N 项确认屏）／批量查看候选
- 候选：多选候选 → 批量比较、批量归档
- **共享同一套选中语义**：两处的多选应由同一个选中模型驱动，而不是各写一套

### #3 画布 ↔ 镜头 ↔ 候选 衔接

- 画布结果能**一键进入候选**
- 能从候选**跳回来源节点**（画布上的生成现场）
- 反过来从候选能定位到画布

**不做自动采用。** `CanvasShotConnections.tsx` 已确立「候选与采用保持分别处理」，这是既定边界。领域上「可用素材／候选选用／明确采用／成片使用」是四个不同事实。

## 3. 硬约束（落地前必须遵守）

### 3.1 多选工具条不得直接触发付费批量执行

`docs/implementation/18-canvas-workspace-contract.md:25`：「多选 ── 移动、删除呈现、分组、共同作为参考；**不批量展开输入框、不一键执行多个付费任务**」。`docs/design/core-workspace-recommendation-v0.2.md:119` 同义。

批量的触发面必须是**多选之后的 N 项明细确认屏**，沿用 #1 已建立的模式：

| 允许 | 禁止 |
|---|---|
| 多选工具条只提供「查看 N 项的生成计划」这类**导航动作** | 工具条上直接「批量生成」把 N 个任务发出去 |
| 确认屏内展示逐项输入、逐项阻断原因、合计、逐项计划身份 | 工具条上批量展开 N 份输入框 |
| 确认屏内显式确认后执行 | 任何自动采用或自动进候选 |

依据：`01-product-requirements.md:50`（批量 UI 可以创建多个独立计划）与 `docs/design/model-integration-architecture-v0.1-2026-09-15.md:312`（编排成一个 `GenerationBatch` 下的多个固定计划／作业；**批次只是分组，不是第二套调度**；部分成功时保留成功结果，不重跑整批）。

### 3.2 费用只能如实显示

后端**没有预算机制**，只有配额闸门（`generation_submission_allowed`：`daily < max_daily_jobs`、`pending < 100`）。当前适配器的估价是硬编码的零，且插入后不可变。

- 「合计估价」目前只能是 **0 CNY**，并沿用 `model.ts` 里 `basisNote` 的诚实写法
- **不得为填满面板而编造价格**
- 提交前校验该挡的是**配额、能力失效、参考素材未验收、画布版本漂移**，不是预算

## 7. 拆分判断

「多选 → 批量动作 → 衔接」是一次选中、多种去向，属**一个可独立审查的切片**，因此合为一个 PR。

**唯一例外**：若 #3 的落地需要**新的领域对象或持久化**（例如记录"候选来源节点"），那已经超出「多选」的延伸范围，应拆成第二个 PR。此判断在实施中做出，不预设。

### 8.4 一条既有的不稳定用例

`CW-13: concurrent selection retains reason…; revoked collaborator cannot display cached list` 在本分支之前的 `main`（PR #62 合入后）就失败过一次，失败点在撤权后点击「刷新列表」时元素已从 DOM 脱离。根因：撤权到达页面有两条路。手动「刷新列表」让列表在弹窗内被「操作未完成」替换；项目事件流（`ProjectUpdates.tsx` 的 `access_revoked`）则重读项目本身，整个项目视图被提示替换、弹窗随之关闭。两条都对，谁先到是竞争；用例原来只认第一条，并且把断言限定在弹窗内。本地重复 5 次复现了第二条路（弹窗已关闭，提示出现在主区域）。修法：手动刷新改为可选动作，断言提到页面级——出现「操作未完成」提示、页面上不再有「镜头顺序」导航、撤权者读取 selection 得 404。本地对该用例重复 8 次通过。

## 9. 中途建成又移除的部分（2026-09-21）

实施中先按 §2 建成了：跨渲染树的选中存储、镜头多选与「批量查看候选」总览、候选多选与并排比较、画布结果节点上的「登记为镜头候选」（预填用途与整段区间）。独立审查证实了这些实现并修掉 10 处问题后，**用户确认把候选挑选改为缩略图方案，并同意移除这一层**。移除理由：

| 移除 | 理由 |
|---|---|
| 「登记为镜头候选」 | 建立候选是镜头级决定，画布上的结果节点说不出"这是哪一镜"；已批准的画布基线也要求画布不碰领域事实。该流程归镜头列表 |
| 候选并排比较、跨镜头总览 | 只能从候选工作台到达，而它的场次入口已收敛为旧深链，普通路径到不了；同镜头内的两条对比已由缩略图上的「对比」覆盖 |
| 选中存储与多选语义 | 唯一消费者就是上面两处；没有可作用的批量动作时，多选是没有目的的状态 |

历史里保留了"先造后删"的提交（`7660ecf`、`9625daa`、`a5aad0d`、`376af04` 建，`d025dd9` 删），按仓库规矩未折叠。独立审查中关于区间预填、种子 key、`nodeActive`、归档媒体门控的结论，凡涉及仍保留的代码（种子 key、`nodeActive`）已落地；其余随移除一并失效。

## 10. 延后事项

| 项 | 决定 | 去向 |
|---|---|---|
| **跨镜头并排看**（"整场过一遍"） | **延后**（用户 2026-09-21 确认）。这是第 1 步立项的核心动机，本片没有交付；同镜头两条对比不能替代它 | 并入定稿计划第 2 步 #4「并列比较多个结果」，在镜头列表的主路径上做，不再放在旧候选工作台 |
| 多选镜头 → 批量生成 | #1 的批量是画布节点粒度，合同里没有按镜头的批量操作 | 单独一个 PR（含契约） |
| 多选候选 → 批量归档 | 领域里没有这个事实：`Take` 无 `status`，`Selection` 只追加 | 需先确认领域设计 |
| 画布素材浏览器多选 | 与素材库（问题 02）共享同一块地 | 由素材库一侧先落 |
| 候选缩略图悬停即预览、页脚「下一镜」、键盘换候选与采用 | 已同意，各自需要动 e2e | 后续小切片 |

本片未覆盖、仍待验证：候选缩略图在同一镜头有大量候选时的读取数量（每条一次媒体读取，无上限）；`?node=` 落点在已有其他选中时的行为。
